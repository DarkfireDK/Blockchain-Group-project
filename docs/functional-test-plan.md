# 航班延误保险DApp功能测试方案

版本：2026-11-11；依据当前本地源码设计。本文件是待执行方案，不代表以下全部用例已经运行。

## 1. 目标与范围

验证“LP注资 → 旅客购保 → NFT保单 → 达标延误赔付 / 到期退款”闭环，以及保单转售后的受益权变化。兼顾钱包、授权、角色、失败回滚和前端数据一致性。业务是否成功以交易回执、合约状态和余额为准，不能只看页面成功提示。

本轮以Hardhat本地链为主；Sepolia只在实际部署并验证后进行验收。不使用真实USDC或主网资产。Slither扫描、经济模型评价和完整攻击审计属于其他验证工作，不用功能测试通过代替。

## 3. 当前规则与检查口径

- 保额范围为10–5000测试USDC，包含上下界。最小单位下：premium=ceil(coverage/50)，refundable=floor(premium/2)。保费、退款额必须与合约quotePolicy一致。
- 购买要求未来的coverageStart，departure>=coverageStart且departure<coverageEnd，保险区间不超过7天；航班号按UTF-8字节长度校验2–12，建议测试使用ASCII航班号。
- 赔付报告窗口为[departure,G]，退款窗口为(G,+∞)。报告必须达到保单购买时固定的门槛；0分钟报告被Oracle拒绝。未达标报告整笔回滚，不会记录为已报告。
- NFT状态：None=0、Active=1、Claimed=2、Expired=3。赔付/退款时NFT销毁，但getPolicy仍保留最终状态。终态ownerOf应失败，不应把“查不到持有人”误判成保单数据丢失。
- 转售必须在departure之前；起飞时刻起不允许挂单或成交。允许挂单不等于市场已有NFT转移权限。
- LP净资产totalAssets=余额−未结算保费；可用资金availableLiquidity=max(余额−锁定保额−退款准备金,0)。两者含义不同，不能用可用资金为新LP定价。
- 暂停仅禁止新购保，已有保单的理赔和退款继续开放。

P0为资金、权限或主要流程，必须通过；P1为输入、展示、恢复及补充边界。下表“自动化”包含拟补充用例，不代表已实现全部断言。

## 5. 三条可直接执行的浏览器主流程

### 场景一：注资—购保—理赔

1. 清空或新建本地测试环境，记录6份合约地址；L1领取足够测试币并向Pool授权、存入10000。
2. 切换U，确认当前网站账户授权，领取1000测试USDC；创建未来航班保单，保额500。
3. 确认报价10、可退5；先授权Pool，再购买，记录policyId及两笔交易。
4. 检查U余额990，NFT属于U且Active；池余额10010、NAV10000、可用资金9505、锁定500、退款准备金5、未赚风险费5。
5. 在本地自动化环境将区块时间推进至departure；浏览器普通页面无法修改时间，使用测试fixture/测试辅助环境，绝不能在Sepolia尝试时间旅行。
6. 由实际报告者A上报60分钟。检查U余额1490、池余额9510、NAV9510、准备金与未赚风险费均0，getPolicy为Claimed，ownerOf失败。
7. 再次报告或结算，确认U余额不再增加。

### 场景二：购保—未出险—到期退款

新建独立环境，重复场景一前4步。推进至G时退款应失败；推进至G+1后由X触发退款。U余额995，池余额10005、NAV10005，所有准备金清零，保单Expired且NFT销毁；X不收到退款。此场景与理赔场景不能使用同一已终结保单。

### 场景三：购保—转售—向新持有人结算

新建独立环境购保。U在起飞前单张授权NFT并挂牌20；B初始余额1000，先授权市场20再购买。确认U余额1009.6、B余额980、手续费地址增加0.4，NFT归B且挂单关闭。随后在有效报告窗口报告60分钟，B余额1480，U余额不再增加。另建一张转售保单验证到期退款归B。

以上余额均为MockUSDC，不包含测试ETH Gas。如果管理员与手续费地址或交易方重合，必须按账户合并计算差值，不能直接套用三个独立地址的余额。

## 6. 自动化与浏览器分工

自动化负责所有精确时间/金额边界、角色拒绝、回滚、NFT状态、准备金和份额；浏览器负责MetaMask真实授权、拒签、网络切换、双账户展示、加载状态及刷新恢复。管理员账户若不在MetaMask中，使用本地测试脚本执行其操作，不向他人索取私钥。

现有Insurance.ts已有20项功能及安全回归用例，覆盖主流程、部分报价和时间边界、条款快照、转售、准备金、公平份额、重入及捐赠攻击。walletAuthorization.test.ts已有6项纯逻辑检查。**这些不能视为本方案所有参数组合、全部浏览器用例或用户当前MetaMask连接已通过。** 建议优先补齐余额不足、完整上下界、转售后退款、市场授权失败回滚及前端恢复。

运行已存在的测试（项目根目录）：
```powershell
node .yarn/releases/yarn-4.13.0.cjs test
node .yarn/releases/yarn-4.13.0.cjs workspace @se-2/hardhat exec tsx --test scripts/walletAuthorization.test.ts
```

本次只设计方案，没有重新运行上述测试，也没有执行本方案新增用例。

## 7. 执行顺序、分工与通过标准

建议按钱包/测试币 → LP → 购保 → 理赔/退款 → 市场 → 管理/恢复执行；3–5人分别负责合约、前端钱包、资金核对与缺陷复测。每轮确定一名记录人。P0失败后先记录并修复，不能以后续截图掩盖。

交付通过标准：所有适用P0用例通过，无未解决资金损失、错误受益人、越权或重复支付缺陷；适用P1全部执行并明确记录残留问题；正常和拒绝路径均有证据。功能按钮或路由尚未提供时标记“未实现/阻塞”，不记通过。功能测试结束不等于安全审计通过。

每次记录：用例ID、执行人、日期、源码提交/本地修订、链ID与合约地址、交易前状态、步骤、交易哈希与回执、交易后余额/状态、实际结果、通过/失败/阻塞/未执行、缺陷编号与复测结果。截图只能辅助，关键资金断言需链上值或自动化日志。
